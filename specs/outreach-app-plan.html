From Scripts to Send File

Forty-nine scripts, one 219-column CSV, and a message-writing step that only works when a human is sitting in the terminal. Here is the whole pipeline, what actually blocks the handoff, and how it becomes an app a VA can run alone.

01

What we actually built

Ten stages, reconstructed from the repo rather than from memory. Six are production, three are archaeology, and one — Stage 0 — has never existed in code at all.

00

Source acquisition

Two independent inputs joined later on domain: a Crunchbase company export (999 rows — domain, name, industry, description, founder, funding, stale traffic) and a people file with names, titles, LinkedIn URLs and emails. Nothing in the codebase produces either, so the app starts with two uploads on one screen.

01

Normalize

column_utils.py auto-detects website, company and traffic columns across CSV shapes. Domain normalization is reimplemented in three separate files — one canonical normalizer, one canonical key.

02

Enrichment fan-out — all the cost, all the flakiness

Eleven modules per company: tech stack, PageSpeed lab and CrUX field data, fresh SimilarWeb traffic, Jina content extraction plus LLM scoring, Playwright screenshot plus Gemini Vision, AI-readiness, SSL and mixed content, consent-before-cookies, accessibility violations, page gating, and twenty-odd data-quality flags.

orchestrator.py runs it sequentially, one company at a time, 1.5s apart, saving every fifth row behind an interactive resume prompt. 999 rows took days and several hand-driven repair passes.

03

Grade and gate

999 rows in; 795 graded, 155 invalid, 49 dead — a gradeable pool of 793. Priority flags, a batch report, and a funnel CSV come out the other side.

04

Evidence bundles

Per-prospect audit bundle plus a shared data dictionary; median bundle 2,194 characters; a first name for 631 of 793.

05

Message generation — the stage with no automation story

v1 Gemini two-pass, abandoned on quality. v2 Sonnet 5 via the Batch API — all 795 generated, zero QA flags, campaign pulled anyway; it also silently dropped the message-2 opener on ~135 of 359 and capitalized case-study slugs into 404s. v3 Claude writing in the terminal, sixteen prospects a cycle: 594 of 793 written, paused since 21 July.

06

QA

About twelve regex rule families — niche openers, placeholder stats, scale framing, the banned CTA, speed words in a non-performance message, funding amounts, brand casing, mechanics, tone, case-study validity, the performance gate. Flags split into deterministically fixable and needs-regeneration. Standing rule: never --fix, that path spends money.

07

Contact resolution

Join people on normalized domain, rank with a three-tier scorer (marketing owner > founder > everyone else, role affinity inside each tier), pick one contact per company, substitute the real first name, then a hard completeness gate.

08

Export

462 sendable rows of 594 written. 132 — 22% — have no contact at all.

09

Post-hoc verification

Case-study metrics traced back to real studies, live signal re-checks, and site-change detection for prospects audited months before the send.

Known defect, already diagnosed

The bundle feeds the model grader opinion — design score, design reasoning — and drops the evidence: named customers and hard metrics that sit fully populated in content_reasoning. This is the recorded root cause of weak, repetitive messages. Fixing the bundle is probably worth more than any model choice.

02

Why it can't be handed over as-is

Four structural blockers. Each has already caused a real incident in this project — these aren't hypotheticals.

Blocker 1

A 219-column CSV is the database

Every stage rewrites the whole file. That produced: a script silently overwriting the live campaign until it was parameterized; eleven .bak files serving as version control; 256 of 594 rows missing review columns because assembly never enforced its schema; and four deleted dead rows resurrecting themselves, because "already written" is derived from presence in a file rather than a status column. Not logic bugs — the absence of a primary key.

Blocker 2

Operations are env vars, and mistakes are destructive

The working command carries three environment variables, and the documented consequence of forgetting one is overwriting the live campaign. A separate flag spends money. That is not a surface you hand to someone else.

Blocker 3

Generation is a person in a terminal

594 messages exist because Claude wrote them sixteen at a time across two sessions, with corrections landing mid-run — the CTA ban arrived at message 412 and needed a 420-instance find-and-replace afterwards. There is no unattended path to message 595.

Blocker 4

The prompt isn't in version control

The 44.5 KB master prompt — the actual product — is gitignored and lives on one disk. The same rules are restated in the run playbook and re-encoded as regexes in the QA script: three copies that can drift, one of them unbacked.

03

Target architecture

What the VA sees

Screen 1

Batches

Campaigns, status, counts, cost to date. One button: new batch.

Screen 2

Run

Upload both CSVs, then a stage board — normalize, enrich, grade, generate, QA, contacts, export — with live counts, failures, and a running cost meter.

Screen 3 — the one that matters

Review queue

One card per prospect: evidence on the left, three messages on the right, QA flags inline. Approve, edit, regenerate, skip.

Screen 4

Export

Send file plus exclusion lists, with a one-screen summary: sendable, no contact, rejected, skipped.

What runs behind it

FastAPI, Postgres and a Redis-backed worker, deployed, with keys in server environment rather than on anyone's laptop. Every stage becomes an idempotent per-company task keyed on batch, domain and stage, with its own status row — resume stops being a hand-written feature and becomes a property of the system. Per-provider token buckets throttle Gemini, Jina, PageSpeed and Apify, and a bounded pool caps concurrent browsers.

Data model

batches      (id, name, created_at, status)
companies    (id, batch_id, domain, name, source_row jsonb)   -- UNIQUE(batch_id, domain)
enrichment   (company_id, stage, status, payload jsonb, error, cost_cents, updated_at)
people       (id, batch_id, domain, full_name, title, linkedin, email, raw jsonb)
messages     (id, company_id, version, m1, m2, m3, signal_category, chosen_signal,
              reasoning jsonb, model, prompt_version, status, qa_flags jsonb)
contacts     (company_id, person_id, rank_score, chosen bool)
prompts      (id, name, version, body, created_at)
exports      (id, batch_id, created_at, row_count, file_path)

messages.status is one of draft, flagged, approved, rejected — and nothing exports without approved. The 219 columns collapse to roughly 25 typed ones (everything downstream code actually reads) plus jsonb for the remainder.

04

The generation service

This is the crux, and it is not simply "call the API instead of typing." What made the in-session writing good was four things, and each needs its own mechanism or the app regresses straight back to v2 — which was QA-clean and still got pulled.

What worked in-sessionMechanism in the service
Deep per-prospect reasoning through the signal decision orderOpus 5, adaptive thinking, effort high
Rich evidence in the inputBundle v2 — carry customer names and hard metrics, not just grader opinion
Seeing the whole batch: that 412 of 594 messages closed identically, that one case study carried 52% of second messagesDiversity budget and batch lint. This is precisely what a stateless per-prospect call cannot do — and precisely what v2 got wrong
Correcting the rules mid-runVersioned prompts plus regenerate-affected-subset

Request shape

system = [
  { SKILL.md body,      cache_control: ephemeral, ttl "1h" },   // ~11k tokens
  { data dictionary,    cache_control: ephemeral            },   //  ~2k tokens
  { case-study registry },                                       // ~1.5k tokens
]
messages = [
  { role: "user", content: prospect bundle + diversity constraints }   // ~700 tokens
]
model         = "claude-opus-5"
thinking      = { type: "adaptive" }
output_config = { effort: "high", format: json_schema(<18-field result>) }

Three things this buys. Structured outputs replace the "return only valid JSON" prose and the parse-retry loop, killing a whole class of v2 failures at the source. The cached prefix stays byte-identical across the batch, so every call after the first reads it at a tenth of the price — volatile content goes after the last breakpoint, and a batch ID must never be interpolated into the system prompt. And every message records its prompt_version, so "the rule changed, regenerate everything written under v3" becomes a query rather than a find-and-replace.

Solving statelessness

  • Diversity budget, injected per request. Before each call the service computes, from the batch so far, which closing phrasings are saturated and which case studies are at quota, and passes a short constraint block in the user turn. Cheap, leaves the cache intact, aimed directly at the observed failure.
  • Case-study quota as a hard post-check. Eight studies in the registry; no single one above roughly 30% of a batch. Deterministic — the model isn't involved.
  • Batch-level lint after generation. N-gram frequency across closing lines and openers, plus case-study and signal-category distribution. Anything above threshold gets a repetition flag into the review queue. This is what a person reading 594 messages does, and it automates cleanly.

Post-processing and the QA gate

Per result, all deterministic and free: sanitize, brand-casing backstop, lowercase URLs, restore the message-2 opener, then run the QA rules. Mechanical and case-study flags are auto-fixed. Anything else gets one bounded regeneration with the failed rule appended as a steer, capped at two attempts. Still flagged after that, it goes to the review queue — never straight to export.

The review queue is not optional

The v2 lesson is exact: 795 messages, zero QA flags, campaign pulled. Regex QA proves the absence of banned patterns; it cannot prove a message is good. So nothing exports without approval. Give the VA an approve-all for clean pages, but flagged messages get handled one at a time — and track approve, edit and reject rates per prompt version, because that becomes the quality signal for every future prompt change.

Measured from this repo — master prompt 44,587 characters, data dictionary 7,625, median bundle 2,194.

Recommendation: Opus 5 at high effort with adaptive thinking and structured outputs — Batch API for the bulk pass, realtime for single regenerations out of the review queue.

Not Sonnet. The earlier Sonnet-versus-Opus comparison was run while the org was out of credits and cost dominated the decision. At twenty-four to forty-eight dollars a campaign against ten-to-twenty-thousand-dollar deals, cost is not a real constraint — and the pulled v2 campaign is direct evidence the cheaper path lost money rather than saving it. Keep Sonnet configurable for a "draft everything cheaply, curate hard" mode if that's ever wanted.

Two Batch API caveats to build around

Results come back out of order — key on the custom ID, never on position. And the server-side fallback parameter is rejected on Batches, so handle a refusal stop reason yourself and requeue those on the realtime path.

The prompt becomes a first-class object

The master prompt moves into the prompts table — and gets force-added to git today, before any app code exists. Every message records the version that wrote it, so the app can eventually offer: "412 messages were written under v3, the rule changed, regenerate them." That's the operation we last performed by hand.

06

Risks and open items

The biggest one isn't messaging

Contact sourcing is the real bottleneck. 132 of 594 written messages can't be sent because the people file has nobody at that domain, and the contact mix is 383 founders to 38 marketers because only about twenty marketing titles exist in the entire dataset. More writing does not fix this. The app should surface it per batch, but the actual fix is a people-enrichment step — worth slotting around Phase 3.

  • Gemini's free tier is 20 requests a day, which throttles grading to roughly ten sites daily. Enrichment can't be a self-serve button until that account is on paid billing.
  • Some sites never grade. Cloudflare and bot detection need a terminal "couldn't grade" state, not an infinite retry loop.
  • Signal freshness. A site audited in June may have relaunched by August — there's already a change-detection script because this bit us. Every message should carry an audit date, and export should warn when the evidence is stale.
  • LinkedIn terms of service. Export-only is the right call. Keep it that way.
  • The rules live in three places — prompt prose, run playbook, QA regexes. Phase 2 should make the prompt the single source and cross-check the QA rules against it.
